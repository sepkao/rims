# RIMS — Inventory Implementation Status

อัปเดตล่าสุด: 1 กันยายน 2026

เอกสารนี้สรุปสถานะฟีเจอร์ Inventory ที่มีอยู่ในโค้ดปัจจุบัน และรายละเอียดการแก้ไขรอบล่าสุดก่อนนำขึ้น Git โดยแยกจาก `rims_scope_lock_v2.md` ซึ่งใช้ล็อก requirement ของระบบ

## สรุปสิ่งที่ทำในรอบล่าสุด

- ปรับหน้ารับของให้เลือกวัตถุดิบจากทะเบียน `ingredients` เท่านั้น เพื่อลดปัญหาชื่อซ้ำหรือชื่อที่ไม่มีในระบบ
- ให้ระบบกำหนดหมวดวัตถุดิบและพื้นที่จัดเก็บจาก master data แทนการให้ผู้ใช้เลือกเอง
- เนื้อรับเข้าเป็น kg และเก็บใน Freezer โดยคงจำนวนและต้นทุนต่อ kg
- ผักรับเข้าได้ทั้ง kg หรือจำนวนจานเต็ม ถ้ารับเป็น kg ระบบจะแปลงเป็นจำนวนจานเต็มก่อนบันทึกเข้าตู้พักละลาย
- แปลงต้นทุนผักจากบาท/kg เป็นบาท/จาน และบันทึกน้ำหนักส่วนที่ปัดทิ้ง (`roundingLossKg`) ใน system log
- เพิ่ม validation ไม่ให้กรอกจำนวนจานเป็นทศนิยม และป้องกันค่าจำนวน/ต้นทุนที่ไม่ถูกต้องทั้ง frontend และ API
- ปรับรายการ Freezer และ Prep ให้ซ่อนล็อตที่หมดอายุหรือมีจำนวนคงเหลือเป็นศูนย์ โดยไม่ลบข้อมูลออกจากฐานข้อมูล
- ปรับคิวหยิบ FIFO ให้ไม่นำล็อตหมดอายุและล็อตที่หมดแล้วมาใช้งาน
- เพิ่ม automated tests สำหรับกฎการรับวัตถุดิบและการแปลงหน่วย

## ฟีเจอร์ Inventory ที่ใช้งานได้แล้ว

### 1. ทะเบียนวัตถุดิบและ Portion Preset

- Owner และ Staff อ่านรายการวัตถุดิบที่ลงทะเบียนแล้วได้
- แต่ละวัตถุดิบมีหมวด `meat` หรือ `vegetable` และค่า `default_portion_size_kg`
- Owner ปรับค่าน้ำหนักมาตรฐานต่อจานได้
- การรับของและการโอนสต็อกอ้างอิง `ingredientId` จริง ไม่สร้างชื่อวัตถุดิบใหม่จากข้อความที่พิมพ์ในฟอร์ม

### 2. รับของเข้าคลังแบบหลายรายการต่อหนึ่ง LOT

- หนึ่งใบรับของเพิ่มวัตถุดิบได้หลายรายการภายใต้ lot header เดียว
- บันทึกทุกบรรทัดใน transaction เดียว หากบรรทัดใดผิดพลาด ระบบ rollback ทั้งรายการ
- สร้าง `stock_movements` ประเภท `intake` และ `system_logs` สำหรับการรับของ
- ใน log เก็บทั้งค่าที่ผู้ใช้กรอก ค่าที่ระบบบันทึก หน่วย ต้นทุน และน้ำหนักที่ปัดทิ้ง เพื่อให้ตรวจสอบย้อนหลังได้

กฎการจัดเก็บ:

| ประเภท | หน่วยที่รับ | หน่วยที่เก็บ | พื้นที่จัดเก็บ | ต้นทุนที่เก็บ |
|---|---|---|---|---|
| เนื้อ | kg | kg | Freezer | บาท/kg |
| ผัก | kg | plate | ตู้พักละลาย | บาท/จาน |
| ผัก | plate จำนวนเต็ม | plate | ตู้พักละลาย | บาท/จาน |

สูตรกรณีรับผักเป็น kg:

```text
จำนวนจานที่เก็บ = floor(น้ำหนักรับเข้า kg / portion size kg ต่อจาน)
ต้นทุนต่อจาน = ต้นทุนต่อ kg × portion size kg ต่อจาน
rounding loss = น้ำหนักรับเข้า - (จำนวนจานที่เก็บ × portion size)
```

การคำนวณจำนวนจานใช้หน่วยย่อย 0.001 kg เพื่อลดปัญหา floating-point เช่น `0.3 / 0.1` ต้องได้ 3 จาน ไม่ใช่ 2 จาน

### 3. ดูสต็อก Freezer และ Prep

- โหลดล็อตจาก Inventory API และแสดงแยกตามพื้นที่จัดเก็บ
- เรียงตามวันหมดอายุเพื่อช่วยจัดลำดับหยิบ
- หน้า stock แสดงเฉพาะล็อตที่ยังไม่หมดอายุและมี `quantity_remaining > 0`
- ล็อตที่หมดอายุหรือจำนวนเป็นศูนย์ยังอยู่ในฐานข้อมูลสำหรับรายงานและการตรวจสอบย้อนหลัง
- หน้า Expired Goods ของ Owner ยังแสดงล็อตหมดอายุได้ตามปกติ

### 4. โอนเนื้อจาก Freezer ไป Prep แบบ FIFO หลายล็อต

- Staff เลือกวัตถุดิบเนื้อและระบุจำนวนจานที่ต้องการเตรียม
- ระบบคำนวณ kg ที่ต้องใช้จาก portion preset
- เลือกล็อตต้นทางที่ยังสดและมีของเหลือ โดยเรียงวันหมดอายุใกล้สุดก่อน แล้วตามด้วยเวลาสร้างและรหัสล็อต
- รองรับการหักจากหลาย source lot ในคำสั่งเดียว
- ล็อก source lots และทำการหัก/สร้าง Prep lots ใน transaction เดียว
- ไม่รวมหลาย source lot เป็นล็อตเดียว แต่สร้าง Prep sub-lot แยกต่อ source lot และเก็บ `source_lot_id` เพื่อรักษา traceability
- แปลงต้นทุนจากบาท/kg ของ source lot เป็นบาท/จานของ Prep sub-lot
- ปฏิเสธล็อตหมดอายุ ล็อตไม่สด วัตถุดิบที่ไม่ใช่เนื้อ จำนวนเกินคงเหลือ และสต็อกที่แตกเป็นเศษจนสร้างจำนวนจานเต็มตามที่ขอไม่ได้

ลำดับการหยิบในโค้ดเป็นลักษณะ FEFO (วันหมดอายุใกล้สุดก่อน) แม้ข้อความในหน้าจอจะใช้คำว่า FIFO

### 5. การคำนวณวันหมดอายุของ Prep เมื่อมาจากต่าง LOT

ระบบไม่เฉลี่ยวันหมดอายุและไม่ใช้วันเดียวร่วมกันทั้งคำสั่งโอน แต่คำนวณแยกให้แต่ละ Prep sub-lot จากวันหมดอายุของ source lot นั้น:

```text
Prep expiry = เวลาที่โอน + ((Source expiry - เวลาที่โอน) / 2)
```

ตัวอย่าง ถ้าโอนพร้อมกันจากสองล็อต:

| Source lot | อายุที่เหลือตอนโอน | Prep sub-lot | อายุที่เหลือหลังโอน |
|---|---:|---|---:|
| LOT-A | 8 วัน | Prep-A | 4 วัน |
| LOT-B | 4 วัน | Prep-B | 2 วัน |

ดังนั้น Prep-A และ Prep-B ยังคงเป็นคนละล็อต มีวันหมดอายุต่างกัน และระบบจะนำ Prep-B ซึ่งหมดอายุก่อนขึ้นมาก่อนในการเรียงสต็อก

### 6. ประวัติและการตรวจสอบย้อนหลัง

- การรับของสร้าง movement ฝั่ง intake
- การโอนสร้าง adjustment ฝั่ง Freezer และ intake ฝั่ง Prep
- system log เก็บรายละเอียดการรับของ การแก้ portion preset และผลการกระจาย FIFO แต่ละ source lot
- ล็อตหมดอายุไม่ถูกลบอัตโนมัติ เพื่อให้ยังคำนวณมูลค่าเสียหายและตรวจสอบประวัติได้

## Inventory API ที่มีอยู่

ทุก endpoint ใต้ `/inventory/*` ต้อง login เป็น Owner หรือ Staff และ endpoint โอนสต็อกอนุญาตเฉพาะ Staff

| Method | Path | สถานะ/หน้าที่ |
|---|---|---|
| GET | `/inventory/ingredients` | อ่านทะเบียนวัตถุดิบและ portion preset |
| PUT | `/inventory/ingredients/:id/portion-preset` | Owner แก้ portion preset |
| GET | `/inventory/lots` | อ่านล็อตทั้งหมดพร้อมสถานะ Fresh, Expiring Soon หรือ Expired |
| POST | `/inventory/lots` | รับของหลายรายการแบบ atomic |
| POST | `/inventory/lots/:id/transfer` | โอนเนื้อจาก source lot เดียว (รองรับไว้ใน API) |
| POST | `/inventory/ingredients/:id/transfer` | โอนตามวัตถุดิบแบบ FIFO/FEFO ข้ามหลายล็อต; เป็น endpoint ที่หน้าจอปัจจุบันใช้ |
