# RIMS — Scope Lock v2 (Shabu Restaurant Stock Flow)

> เอกสารนี้แทนที่ framing เดิม (UC1–UC8 ของ schema v3) ทั้งหมด ตามที่ตกลงกัน
> บันทึกทุกจุดที่ "ล็อก" ไว้ในเซสชันนี้ ยังไม่มีการเขียนโค้ด/schema จริง — เป็นเอกสาร scope เท่านั้น

## 1. หน่วยความจำหลัก: นิยาม "ล็อต" (Lot)

- **1 ล็อต = 1 รอบการรับของ (receiving round)** ไม่ใช่ต่อวัตถุดิบ 1 ชนิด
- 1 ล็อตมีได้หลายวัตถุดิบข้างใน (เช่น เนื้อ 100 กก. + ผัก 10 กก. ในรอบเดียวกัน)
- โครงสร้าง: **lot header** (รอบรับของ) + **line items** (รายการวัตถุดิบย่อย แต่ละรายการมี qty/ที่เก็บ/ต้นทุนของตัวเอง)
- **FIFO บังคับแยกเส้นตามวัตถุดิบแต่ละชนิด** ไม่ใช่บังคับทั้งล็อต
  - เนื้อของรอบ 1 ต้องหมดก่อนตัดเนื้อรอบ 2
  - ผักของรอบ 1 ต้องหมดก่อนตัดผักรอบ 2
  - คนละเส้น ไม่ผูกกัน — lot header ใช้แค่ reference/traceability ไม่ได้บังคับลำดับใช้ข้ามชนิดวัตถุดิบ

## 2. Storage Locations (2 ตู้) — แก้ไข 2026-07-15 (F3d, กลับคำ F3c บางส่วน)

> **อัปเดต 2026-07-15 (รอบ 8, F3d):** F3c (คืนเป็น 3 ที่เก็บ) **ถูกแก้บางส่วน** — กลับเป็น **2 ที่เก็บ** อีกครั้ง แต่**ไม่ใช่แบบเดียวกับ F3b เดิม** เพราะยังคงหน่วย "จาน" ของตู้พักละลายไว้ (F3c ข้อ 2/3 ยัง valid) ส่วนที่เปลี่ยนคือ: **ไม่มี "ตู้แช่ผัก" แยกต่างหากอีกแล้ว** — ผักถูกจัดใส่จาน**ทันทีตอนรับของ (UC-N1)** แล้วเก็บเข้าตู้พักละลายโดยตรง เพราะผักเสียความสดไว ไม่มีประโยชน์ที่จะพักไว้ดิบๆ ก่อน (ต่างจากเนื้อที่ต้องแช่แข็งเก็บได้นาน)

| # | ชื่อ | ประเภท | อุณหภูมิ | ใช้เก็บ | หน่วยที่นับ |
|---|---|---|---|---|---|
| 1 | Freezer (ตู้แช่แข็ง) | ตู้แช่แข็ง | ต่ำกว่า 0°C | **เนื้อเท่านั้น** ตอนรับล็อตใหม่ (ดิบ) | kg/g |
| 2 | ตู้พักละลาย | ตู้แช่เย็นธรรมดา (พอร์ชั่นพร้อมเสิร์ฟ) | ~1–4°C | **เนื้อ** ที่โอนย้ายมาจาก Freezer (UC-N2) + **ผัก** ที่จัดใส่จานตั้งแต่ตอนรับของ (UC-N1) โดยตรง | **จาน (servings)** — แยกนับต่อวัตถุดิบ |

- ระบบต้องรู้แค่ **type (freeze/chill)** พอ ไม่ต้อง track อุณหภูมิจริงใน schema (นอกสโคป)
- **Freezer นับหน่วยเป็น kg/g (เนื้อเท่านั้น), ตู้พักละลาย นับหน่วยเป็นจาน (ทั้งเนื้อและผัก)** — `stock_lots` จึงมีหน่วยต่างกันตาม storage_location ที่แถวนั้นอยู่
- **เนื้อ**: Freezer (ดิบ, kg) → **UC-N2 (manual, เฉพาะเนื้อ)** → ตู้พักละลาย (จาน) — **กลับมาเป็น "เฉพาะเนื้อ" อีกครั้ง** (F3c เคยแก้เป็น "ทั้งเนื้อและผัก" — ตอนนี้ยกเลิกส่วนนั้นแล้ว)
- **ผัก**: **ไม่ผ่าน UC-N2 อีกต่อไป** — แปลง kg→จานทันทีที่ UC-N1 (ดูข้อ 3) แล้วเข้า `stock_lots` ในตู้พักละลายเลยตั้งแต่รับของ ไม่มี lot ดิบของผักค้างอยู่ที่ไหน

## 3. UC-N1: รับของเข้าล็อตใหม่ — แก้ไข 2026-07-15 (F3d)

- Kitchen Staff กด "รับของเข้าใหม่" → ระบบสร้าง lot header (เช่น LOT-001) อัตโนมัติ
- กด "+ เพิ่มสินค้า" ทีละชนิด: ชื่อวัตถุดิบ (autocomplete) + จำนวน/หน่วย (กก./กรัม ตามที่ซัพพลายเออร์ชั่งมา) + ที่เก็บ (default ตามชนิด) + ต้นทุน/หน่วย
- ทำซ้ำจนครบทุกชนิดในรอบนั้น
- **แปลงหน่วยทันทีสำหรับผัก (F3d, ล็อก 2026-07-15):** ผักที่กรอกเป็น kg/g จะถูก**แปลงเป็นจานทันทีที่ยืนยันล็อต** — ใช้กฎเดียวกับ UC-N2 (ข้อ 4) ทุกประการ: ใช้ `default_portion_size_kg` ของผักนั้น, **ปัดลง**, เศษที่แปลงไม่ลงตัวหายไปไม่สะสม — แถวที่บันทึกใน `stock_lots` คือหน่วยจาน เก็บเข้า `storage_location = ตู้พักละลาย` โดยตรง (ไม่มี lot ดิบของผักที่ไหนเลย)
  - `unit_cost` ของแถวผักนี้ = บาท/จาน คำนวณจากบาท/กก. ที่กรอก × พอร์ชั่นมาตรฐาน (เหมือนหลักการ waste cost ในข้อ 4)
- เนื้อยังคงกรอกเป็น kg/g ตามปกติ เก็บดิบเข้า `storage_location = Freezer` (ไม่แปลงหน่วยตอนนี้ รอแปลงตอน UC-N2)
- **กด "ยืนยันรับของ" ครั้งเดียว ปิด transaction ทั้งล็อตแบบ atomic** — สร้างหลายแถวใน `stock_lots` พร้อมกัน (บางแถวหน่วย kg/g เช่นเนื้อ, บางแถวหน่วยจานเช่นผักที่แปลงแล้ว) ทุกแถว reference กลับ lot header เดียวกัน (กัน rollback ครึ่ง ๆ กลาง ๆ ถ้าเน็ตหลุด/กดผิด)

## 4. UC-N2: ย้ายเนื้อเข้าตู้พักละลาย — แก้ไข 2026-07-15 (F3d, กลับคำ F3c บางส่วน)

- **Manual, ทำโดยพนักงานเท่านั้น** — ไม่ auto, ไม่ผูกกับออเดอร์
- **ใช้กับเนื้อเท่านั้น** (ย้ายจาก Freezer → ตู้พักละลาย) — **F3d (ล็อก 2026-07-15) ยกเลิกส่วนที่ F3c เคยเพิ่มผักเข้ามา**: ผักไม่ผ่าน UC-N2 อีกต่อไป เพราะถูกแปลงเป็นจานตั้งแต่ตอนรับของแล้ว (ดูข้อ 3/UC-N1) — เหตุผล: ผักเสียความสดไว ไม่มีประโยชน์ที่จะพักดิบไว้ก่อนแล้วค่อยมาย้ายทีหลังแบบเนื้อ
- พนักงานประเมินเองว่าจะดึงเท่าไหร่ (หรืออ้างอิงคำแนะนำจาก UC-N3) → กรอกจำนวนที่ดึงออกจริง (หน่วย kg/g)
- **แปลงหน่วย kg/g → จาน ทันทีตอนยืนยัน UC-N2** (worksheet F3c ข้อ 3, ล็อก 2026-07-15):
  - ใช้พอร์ชั่นมาตรฐานต่อจาน (เช่น เนื้อ 100g/จาน, ผัก 50g/จาน) แปลงจำนวนที่ดึง (kg/g) เป็นจำนวนจานเต็ม
  - **ปัดลง** — เศษที่แปลงไม่ลงตัว (เช่น 5.03 กก. ÷ 100g = 50.3 จาน) **หายไปเลย ไม่สะสมไปรอบถัดไป** (rounding loss, กันเข้าใจผิดว่ามีจานเกินจริง)
  - ตัด (adjustment) จาก lot ต้นทางเต็มจำนวนที่กรอก (หน่วย kg/g) แต่สร้าง sub-lot ใหม่ในตู้พักละลายเป็นจำนวนจานที่ปัดแล้ว (หน่วยจาน)
- ระบบบันทึกเป็น **"internal re-intake"**:
  - ตัด (adjustment) จาก `quantity_remaining` ของ lot ต้นทางใน Freezer (หน่วย kg/g)
  - สร้าง **sub-lot ใหม่** ในตู้พักละลาย (แถวใหม่ใน `stock_lots`, หน่วยจาน, source อ้างอิงกลับไป lot แม่)
  - **เหตุผลที่เลือกวิธีนี้**: รักษา invariant เดิม "1 lot = 1 ที่เก็บเสมอ" ไม่ต้องแก้ schema ที่ทดสอบจบแล้ว ไม่ต้องเพิ่ม movement_type ใหม่ (ใช้ `adjustment` เดิม + insert ปกติ)
- **กฎใหม่ — ลดความสดลงครึ่งหนึ่งสำหรับเนื้อเท่านั้น (ล็อก 2026-07-15):**
  - เมื่อย้ายเนื้อจาก Freezer → ตู้พักละลาย, `expiry_date` ของ sub-lot ใหม่ **ไม่ใช่ค่าเดิมจาก lot แม่** — ต้องคำนวณใหม่โดย **หารอายุความสดที่เหลือลงครึ่งหนึ่ง**:
    ```
    เวลาที่เหลือก่อนหมดอายุ (ณ วินาทีย้าย) = expiry_date เดิมของ lot แม่ − เวลาที่ย้าย
    expiry_date ใหม่ (sub-lot ในตู้พักละลาย) = เวลาที่ย้าย + (เวลาที่เหลือ ÷ 2)
    ```
    ตัวอย่าง: เนื้อ lot แม่เหลืออีก 8 วันจะหมดอายุตอนที่ย้าย → sub-lot ในตู้พักละลายจะเหลืออายุความสดแค่ 4 วัน (ไม่ใช่ 8 วันเดิม)
  - **ผักไม่มีกฎนี้** — ผักไม่ผ่าน UC-N2 อีกต่อไป (F3d) `expiry_date` ของผักตั้งตั้งแต่ตอน UC-N1 ตรงๆ (ไม่มีการคำนวณใหม่/หารครึ่งเลย เพราะไม่เคยผ่านการแช่แข็ง)
  - เหตุผล: เนื้อที่ผ่านการย้ายออกจาก Freezer (ละลาย/พร้อมเสิร์ฟ) เสื่อมสภาพเร็วกว่าตอนแช่แข็งมาก ต้องคุมความปลอดภัยอาหารเข้มขึ้น
- **Waste cost calculation (ล็อก 2026-07-15):** เพราะพอร์ชั่นมาตรฐานต่างกันต่อวัตถุดิบ (เนื้อ 100g/จาน, ผัก 50g/จาน — คนละค่า ไม่ใช่น้ำหนักจริงที่ชั่งใหม่) **จึงไม่บังคับหน่วย "บาท/กก." เดียวทั่วระบบ** — แทนที่ด้วยการแปลง **`unit_cost` เป็นเงินบาทต่อหน่วยของแถวนั้นๆ ตั้งแต่ตอนย้าย**:
  - Freezer (เนื้อดิบ): `unit_cost` = บาท/กก. (ตามที่กรอกตอน UC-N1)
  - ตู้พักละลาย (เนื้อ): `unit_cost` = บาท/จาน คำนวณครั้งเดียวตอน UC-N2 = `unit_cost บาท/กก. ของ lot แม่ × พอร์ชั่นมาตรฐาน (กก./จาน)` แล้วบันทึกลง sub-lot เลย
  - ตู้พักละลาย (ผัก): `unit_cost` = บาท/จาน คำนวณครั้งเดียวตอน **UC-N1** (ไม่ใช่ UC-N2 เพราะผักไม่ผ่าน UC-N2 แล้ว — ดูข้อ 2/3) ด้วยสูตรเดียวกัน
  - `waste_records.waste_cost` (บาท) = `quantity_wasted × unit_cost ของแถวนั้น` — คูณตรงได้ทันทีไม่ว่าจะมาจากที่เก็บไหน เพราะหน่วยถูกแปลงให้ตรงกันแล้ว
  - **AI Task 4 (weekly cost/profit)** แค่ `SUM(waste_records.waste_cost)` ข้ามทุกที่เก็บได้ตรงๆ ไม่ต้องแปลงหน่วยเพิ่ม
  - ต้องมี field `ingredients.default_portion_size` (กก./จาน, แยกต่อวัตถุดิบ) ในตารางที่ยังไม่เคยระบุมาก่อน
- **E2 (ล็อก 2026-07-15, อัปเดต 2026-07-15 รอบ 3):** UC-N2 เป็น **manual form ล้วนๆ** — พนักงานเลือก lot ต้นทาง + กรอกจำนวนที่ดึงเอง **ไม่มี AI parse ภาษาธรรมชาติเข้ามาเกี่ยวเลย** — เดิมมี "AI Task 5" (storage transfer parsing) แยกไว้สำหรับ scenario อื่นที่ไม่ใช่ UC-N2 แต่ **Task 5 ถูกตัดออกจากสโคปทั้งหมดแล้ว** (ข้อ 12) เพราะไม่มี scenario อื่นเหลืออยู่จริงในโมเดล 2 ที่เก็บสุดท้าย

## 5. UC-N3: คำแนะนำเตรียมสต๊อกประจำวัน (AI Feature)

- **สถานะ: ล็อกแล้ว ต้องทำ** (ไม่ข้าม)
- **Trigger**: รันครั้งเดียวตอน Kitchen Staff เปิดหน้า "เตรียมสต๊อกวันนี้" ตอนเริ่มกะ/เปิดร้าน
- **สูตร**:
  ```
  แนะนำดึงเพิ่ม = (ค่าเฉลี่ยยอดใช้ของวันนี้ในสัปดาห์ × buffer safety) − ของที่เหลือในตู้พักตอนนี้
  ```
  - ค่าเฉลี่ยยอดใช้: มาจาก `stock_movements` type `deduction` ย้อนหลัง แยกตาม **วันในสัปดาห์** (เสาร์-อาทิตย์ขายดีกว่าวันธรรมดา)
  - buffer safety: Owner ตั้งเอง (เช่น +15%)
- ตัวอย่าง output: *"วันเสาร์นี้ คาดใช้วากิวประมาณ 22 กก. ตอนนี้เหลือในตู้พัก 5 กก. → แนะนำดึงจาก FREEZE เพิ่ม 17 กก."*
- **Staff ยังต้องกด "ยืนยันจำนวนที่หยิบจริง" เอง** — override ได้ ระบบไม่บังคับตาม
- **Cold start**: ข้อมูลย้อนหลังไม่พอ → แจ้ง "ข้อมูลไม่พอ กรุณากรอกเอง" ตรง ๆ ห้ามเดา
- ต้องมี view ใหม่: ยอดใช้เฉลี่ยต่อวัตถุดิบ แยกตามวันในสัปดาห์ (ยังไม่มีใน schema เดิม)

- ถ้าสต๊อกในตู้พักละลายไม่พอตอนลูกค้าจะสั่ง (ขั้นตอน 3) → **ปฏิเสธออเดอร์ทันที** ไม่ปล่อยผ่านไปถึง confirm ไม่มี fallback ดึงจาก Freezer อัตโนมัติ (สำหรับผัก: ไม่มี fallback อยู่แล้วเพราะไม่มี lot ดิบเหลือให้ดึง — ต้องรอ UC-N1 รอบใหม่เท่านั้น)

## 7. Race Condition Protection (ตัดสต๊อกพร้อมกัน 2 ออเดอร์)

**ปัญหา**: 2 โต๊ะสั่งของชิ้นสุดท้ายพร้อมกัน ทั้งคู่ผ่านเช็คตอน submit (ยังไม่มีใครถูกตัดตอนนั้น) แล้วเข้าสู่ "รอ confirm" พร้อมกัน

**คำตอบ**: การเช็ค + ตัดต้องเป็น **atomic operation เดียวกัน** ไม่ใช่ "เช็คก่อน ตัดทีหลัง"

```sql
UPDATE stock_lots
SET quantity_remaining = quantity_remaining - 1
WHERE lot_id = X AND quantity_remaining >= 1;
```

> **หมายเหตุ 2026-07-15 (F3c):** ตัวอย่างนี้ตัดหน่วย **"จาน"** ในตู้พักละลาย (1 จานต่อรายการที่สั่ง) — เดิมเป็นตัวอย่างหน่วยกรัม (`- 100` / `>= 100`) ตอนที่ตู้พักละลายยังนับเป็น kg/g, ตอนนี้เปลี่ยนหน่วยแล้วตาม F3c ข้อ 2 ในไฟล์ worksheet

- ถ้า `affected rows = 0` → ของไม่พอจริง ณ วินาทีนั้น → **auto-cancel ออเดอร์นั้นทันที** (ไม่ตัดติดลบ)
- หลักการ: **"first-confirm-wins"** — ใครถึง atomic transaction ก่อนได้ของ
- ฝ่ายแพ้ได้รับแจ้งเตือนทันทีว่า "รายการนี้หมดแล้ว เนื่องจากลูกค้าอีกโต๊ะยืนยันก่อน"
- สรุป 2 ชั้นป้องกัน: (1) delay การตัดไปจนถึงจุด confirm ลดโอกาสชนกัน (2) atomic conditional update รับประกันไม่มีทางติดลบ

> **แก้ไข 2026-07-17 (True FIFO splitting, ล็อกระหว่างออกแบบ UC-N12):** เดิม `deduct_stock_fifo` หา**ล็อตเดียว**ที่มีของพอทั้งหมด (`quantity_remaining >= p_plates_needed LIMIT 1`) — ถ้าล็อตเก่าสุดมีของเหลือไม่พอคนเดียว จะ**ข้ามไปล็อตถัดไปทั้งยวง ไม่แตะล็อตเก่าเลย** ทำให้ล็อตเก่าเศษเล็กน้อยตกค้างได้ (เสี่ยงหมดอายุก่อนถูกใช้) — **เปลี่ยนเป็นตัดข้ามล็อตได้จริง**: ไล่ล็อตตาม `expiry_date ASC` ทีละล็อต ดึงเท่าที่มีจากล็อตเก่าก่อนจนหมด แล้วดึงส่วนที่ขาดจากล็อตถัดไปต่อ (เกิด `stock_movements` หลายแถวต่อ 1 การตัด 1 ครั้งได้) — ยังคง**atomic**เหมือนเดิม (เช็กยอดรวมทุกล็อตพอก่อน ถึงจะเริ่มตัดจริง ไม่มีทางตัดค้างครึ่งๆ กลางๆ) — กฎ "ไม่มี partial fulfillment" ระดับ**ออเดอร์**ยังเหมือนเดิมทุกประการ (วัตถุดิบไหนรวมทุกล็อตแล้วยังไม่พอ → ยกเลิกทั้งออเดอร์) เปลี่ยนแค่ระดับ**ล็อต**ให้ไม่ทิ้งเศษเก่าไว้เฉยๆ อีกต่อไป

## 8. UC-N6: คำนวณจำนวนจานที่สั่งได้ (Available Servings)

- เหตุผล: เนื้อใน Freezer ยังไม่ได้พอร์ชั่น เสิร์ฟไม่ได้จริง ต้องแยกสถานะ "มีของในร้าน" กับ "พร้อมเสิร์ฟจริง" ออกจากกัน — ผักไม่มีปัญหานี้เพราะเข้าตู้พักละลายเป็นจานตั้งแต่ต้นแล้ว (F3d)
- **แก้ไข 2026-07-15 (F3c):** เพราะตู้พักละลายนับหน่วยเป็น**จานอยู่แล้ว** (ไม่ใช่ kg/g) การคำนวณจึงเป็นแค่ **อ่านค่า `quantity_remaining` ตรงๆ** ต่อวัตถุดิบ (ไม่ต้องหารด้วยพอร์ชั่นมาตรฐานอีกต่อไป เพราะ conversion เกิดขึ้นแล้วตอน UC-N2) — ถ้าจะโชว์ "เมนูนี้ทำได้กี่จาน" ต้องคำนวณ **min ของทุก ingredient ที่สูตรเมนูนั้นต้องใช้** จากตัวเลขแยกต่อวัตถุดิบเหล่านี้ (worksheet F3c ข้อ 2)
- **สิทธิ์ดู (worksheet F2+F3b, ล็อก 2026-07-14):** actor "พนักงาน" (รวม Kitchen Staff+Waiter แล้ว) — ไม่แยกสิทธิ์ตามบทบาทย่อยอีกต่อไป

## 9. UC-N7: แจ้งเตือนสต๊อกต่ำกว่าเกณฑ์ (Reorder Threshold)

- **Feature 1 — ล็อกแบบ: Owner ตั้งเลขคงที่เอง (static)**
- ใช้ field `ingredients.reorder_threshold` ที่มีอยู่แล้วใน schema เดิม ไม่ต้องแก้อะไรเพิ่ม
- **แก้ไข 2026-07-15 (F3d):** เทียบ **แยกสต๊อกเป็นคนละที่เก็บ ไม่รวมยอดข้ามหน่วย** — และตอนนี้ที่เก็บแต่ละชนิดวัตถุดิบก็ต่างกันเองด้วย:
  - **เนื้อ**: มี 2 threshold แยกอิสระ — Freezer (หน่วย kg, ดิบ) และตู้พักละลาย (หน่วยจาน, พร้อมเสิร์ฟ) ไม่บวกรวมกัน
  - **ผัก**: มี **แค่ threshold เดียว** คือที่ตู้พักละลาย (หน่วยจาน) เพราะไม่มีที่เก็บดิบแยกแล้ว (F3d) — เกณฑ์นี้จึงเป็นตัวเดียวกับที่ UC-N10 ใช้เตือนพนักงาน ต่างกันแค่ผู้รับแจ้งเตือน (Owner vs พนักงาน) และค่า threshold ที่ตั้งแยกกันได้
  - **เหตุผลที่ไม่รวมยอดข้ามหน่วย**: 1 kg เนื้อใน Freezer ไม่เทียบเท่ากับปริมาณที่ได้จริงในตู้พักละลาย เพราะเนื้อเสื่อมสภาพ/ลดความสดลงครึ่งหนึ่งระหว่างย้าย (ดูกฎใหม่ข้อ 4/UC-N2)
  - **แยกจาก UC-N10** (ข้อ 14) ซึ่งเตือนพนักงานเรื่องตู้พักละลายต่ำแบบ operational คนละ actor/จุดประสงค์กัน — สำหรับเนื้อ UC-N7 กับ UC-N10 ต่างกันแค่ **ใครเห็น** (Owner vs พนักงาน) และ **threshold แยกอิสระต่อกัน** แต่สำหรับผัก UC-N10 **ไม่มี action ให้ทำจริง** (ไม่มี lot ดิบให้ไปย้ายเพิ่มแบบเนื้อ) จึงอาจไม่จำเป็นต้องมี UC-N10 แยกสำหรับผัก — ให้ UC-N7 (แจ้ง Owner สั่งซื้อเพิ่ม) เป็นกลไกเดียวพอสำหรับผัก — **ยังไม่ล็อกส่วนนี้ ต้องถามยืนยัน**
- ต่ำกว่า → DB trigger ยิง notification `low_stock` ทันที (ไม่ใช้ AI, logic ตรงไปตรงมาระดับฐานข้อมูล)
- **เหตุผลที่ไม่เลือก auto-calculate**: ซ้ำซ้อนกับ Feature 2 และ Feature 3 ที่คำนวณจากยอดใช้เฉลี่ยอยู่แล้ว เพิ่ม logic ซ้ำโดยไม่ได้ประโยชน์เพิ่มจริง

## 10. UC-N8: คำแนะนำสั่งซื้อรอบถัดไป (Procurement Recommendation — AI Feature)

- **สถานะ: ล็อกแล้ว ต้องทำ**
- **Output ต้องเป็นตัวเลขชัดเจน** เช่น *"รอบหน้าแนะนำสั่งเนื้อ 130 กก. เพิ่มจากเดิม 100 กก."* (ไม่ใช่แค่ flag เตือนเฉย ๆ)
- **สูตร**:
  ```
  แนะนำ = ค่าเฉลี่ยยอดใช้ล่าสุด × (1 + % เทรนด์เทียบรอบก่อนหน้า) × buffer safety
  ปัดเป็นหน่วยที่ซื้อได้จริง (ตาม pack size ของซัพพลายเออร์ ถ้ามีข้อมูล)
  ```
  - ข้อมูลยอดใช้: จาก `stock_movements` type `deduction` ย้อนหลัง N รอบ (เช่น 4 สัปดาห์)
- **ขอบเขต**: เป็นแค่คำแนะนำ Owner ตัดสินใจสั่งจริงเอง — **ไม่มี auto-PO ไปซัพพลายเออร์** (ไม่มี supplier integration ในสโคปนี้)
- **Cold start**: ข้อมูลไม่พอ → บอกตรง ๆ ว่าแนะนำไม่ได้ ห้ามเดาตัวเลขมั่ว ๆ

## 17. UC-N12: คืนสต็อกจานที่ยังไม่เสิร์ฟกลับเข้าตู้พักละลาย (ใหม่ — ล็อก 2026-07-17)

**สถานการณ์**: ลูกค้าไม่เอา/สั่งผิด/พนักงานหยิบผิด — จานอาหารยังไม่ถูกวางที่โต๊ะลูกค้าเลย (`orders.served_at IS NULL`) แต่สต็อกถูกตัดไปแล้วตั้งแต่ตอน System auto-confirm (ตามข้อ 6) ต้องคืนกลับเข้าสต็อกโดยรักษาความสดเดิม (ล็อต/วันหมดอายุเดิม)

**ตัดสินใจแล้ว:**
- **ระดับที่คืนได้**: รายจาน (ต่อ `order_item`) ไม่ใช่ทั้งออเดอร์ — รองรับคืนบางส่วนด้วย (สั่ง 3 จาน คืนแค่ 1 จานได้)
- **สิทธิ์**: พนักงานกดคืนได้เองทันที **ไม่ต้องผ่าน Owner อนุมัติ** (ต่างจาก waste_records ที่ต้อง confirm — เพราะนี่คือแก้ error ปฏิบัติงาน ไม่ใช่ของเสีย)
- **เงื่อนไข**: คืนได้เฉพาะตอน `orders.served_at IS NULL` เท่านั้น (เสิร์ฟไปแล้วคืนไม่ได้)
- **กลไกคืน**: คืนกลับเข้า**ล็อตเดิมที่ถูกตัดไปเป๊ะ** (ไม่สร้างล็อตใหม่) — ไม่แตะ `expiry_date` เลย ความสดจึงเท่าเดิมโดยอัตโนมัติ และล็อตนั้นกลับเข้าคิว FIFO ปกติทันที (แก่กว่าล็อตอื่นเหมือนเดิม ถูกตัดก่อนในออเดอร์ถัดไป)
- **ถ้าตอนตัดสต็อกข้ามหลายล็อต** (ตาม true FIFO splitting ข้อ 7) — คืนกลับ**ตามลำดับเดียวกับตอนตัด** (ล็อตเก่าสุดที่เคยถูกตัดก่อน ได้คืนก่อน) จนกว่าจะครบจำนวนที่คืน
- **สถานะการคืน**: ไม่มี column แยก — derive จาก `order_items.quantity_returned` เทียบกับ `quantity` (0=ยังไม่คืน, 0<x<quantity=คืนบางส่วน, x=quantity=คืนครบ) หลีกเลี่ยงข้อมูล 2 จุดที่ต้องซิงค์กันเอง

**Schema ที่เพิ่ม** (ดู `rims_database_schema.sql`):
- `order_items.quantity_returned INT DEFAULT 0` (เช็คไม่เกิน `quantity`)
- `stock_movements.order_item_id` (ผูกการตัด/คืนแต่ละแถวกับจานที่แน่นอน — จำเป็นเพราะ 1 ออเดอร์มีได้หลายเมนู)
- `stock_movements.movement_type` เพิ่มค่า `'return'`
- Function ใหม่ `return_order_item_to_stock(order_item_id, quantity, actor_id)`
