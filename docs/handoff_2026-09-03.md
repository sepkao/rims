## 1. Business rules ที่ตกลงแล้ว

### Kitchen Queue และ Serving Queue

- `Kitchen Queue` ใช้โดยพนักงานครัวเพื่อดูคำแนะนำ/สถานะการเตรียมวัตถุดิบและรับทราบออเดอร์
- `Serving Queue` ใช้โดยพนักงานเสิร์ฟเพื่อดูออเดอร์ที่ต้องนำไปเสิร์ฟและยืนยันว่าเสิร์ฟแล้ว
- สองหน้ามีหน้าที่ต่างกัน จึงต้องคงไว้ทั้งคู่

### Menu และ Prep stock

- Owner สร้างเมนูจากวัตถุดิบที่ลงทะเบียนแล้ว
- BOM ระบุจำนวนถาดจาก Prep ที่ใช้ต่อเมนูหนึ่งชุด
- จำนวนเมนูพร้อมขายคำนวณอัตโนมัติจาก Prep stock โดยใช้วัตถุดิบที่ทำจำนวนชุดได้น้อยที่สุด
- หาก Prep stock หมด เมนูไม่ต้องถูกตั้งค่าใหม่ เมื่อเติม Prep stock ระบบจะคำนวณจำนวนพร้อมขายกลับมาอัตโนมัติ
- Owner สามารถหยุดขายเมนูด้วย `is_active`
- การแก้ BOM มีผลกับออเดอร์ใหม่เท่านั้น ออเดอร์เก่าใช้ BOM snapshot ตอนสร้างออเดอร์
- เมนูมีรูปได้หนึ่งรูป รองรับ JPG, PNG และ WebP ขนาดไม่เกิน 5 MB
- เมนูมีหมวดหลักหนึ่งหมวด เช่น เนื้อสัตว์, ผัก หรือเซ็ตคอมโบ
- แนวทาง Tags หลายค่าได้รับการเห็นชอบเชิงออกแบบ แต่ **ยังไม่ได้ implement** อย่าสับสนกับ menu categories

### Inventory และของหมดอายุ

- Dashboard, Stock mix และ FIFO นับเฉพาะล็อตที่ `quantity_remaining > 0`
- ล็อตยอดศูนย์ไม่แสดงใน active stock แต่ยังคงอยู่ใน Inventory history
- ล็อตหมดอายุหรือ `is_not_fresh = true` ห้ามใช้ใน Freezer/Prep/FIFO
- การยืนยันแยกทิ้งทำได้โดย Owner เท่านั้น แม้ Staff จะพยายามเรียก API โดยตรงต้องได้ `403`
- การแยกทิ้งตัดยอดทั้งหมดเป็นศูนย์และบันทึก `stock_movements`, `waste_records` และ `system_logs` ใน transaction เดียว

### Ingredient registry และ portion preset

- Staff สามารถสร้างชื่อวัตถุดิบใหม่จากหน้ารับของ เพื่อให้ระบบสร้าง ingredient ID ก่อนรับล็อต
- Staff กำหนดได้เฉพาะชื่อและหมวดวัตถุดิบ ไม่สามารถกำหนดน้ำหนักต่อถาด
- ระบบตั้งค่าเริ่มต้นภายในเป็น 100 g สำหรับเนื้อสัตว์และ 50 g สำหรับผัก เพื่อให้ record ใช้งานได้ตาม schema
- Owner ต้องตรวจและกำหนด portion preset จริงภายหลัง
- หน้า Owner แสดงและรับค่า portion preset เป็นกรัม เช่นกรอก `350`; API/DB ยังคงเก็บ `0.350 kg` ภายใน

## 2. การเปลี่ยนแปลงหลัก

### API (`apps/api/src/index.ts`)

- เพิ่ม metadata เมนู: category, image และจำนวนพร้อมขายจาก Prep
- เพิ่มการอัปโหลด/อ่านรูปเมนู
- เพิ่ม BOM snapshot ตอนสร้าง order item
- เพิ่ม CRUD ทะเบียนหมวดหมู่เมนู
- เปลี่ยนการลบเมนูเป็น soft delete เพื่อไม่ทำลายออเดอร์และ BOM เก่า
- เพิ่ม API สร้าง ingredient ใหม่สำหรับ Owner/Staff โดย portion preset ถูกกำหนดจากระบบ ไม่รับค่าจาก Staff
- เพิ่ม API แยกทิ้งล็อตหมดอายุสำหรับ Owner เท่านั้น
- เพิ่ม/ปรับ Staff order endpoints สำหรับ acknowledge และ serve

Endpoints ที่เกี่ยวข้อง:

| Method | Path | สิทธิ์/หน้าที่ |
|---|---|---|
| GET | `/menu-items` | รายการเมนูสำหรับ Internal UI |
| GET/POST | `/owner/menu-categories` | อ่าน/เพิ่มหมวดเมนู (Owner) |
| PUT/DELETE | `/owner/menu-categories/:id` | เปลี่ยนชื่อ/ลบหมวด (Owner) |
| POST | `/owner/menu-items` | สร้างเมนูและ BOM (Owner) |
| PUT/DELETE | `/owner/menu-items/:id` | แก้ไข/soft-delete เมนู (Owner) |
| PUT | `/owner/menu-items/:id/image` | อัปโหลดรูปเมนู (Owner) |
| GET | `/customer/menu-items` | เมนูที่ active, ไม่ถูกลบ และสั่งได้ใน session |
| POST | `/inventory/ingredients` | สร้าง ingredient ID (Owner/Staff) |
| PUT | `/inventory/ingredients/:id/portion-preset` | แก้ preset (Owner เท่านั้น) |
| POST | `/inventory/lots/:id/dispose` | แยกทิ้งล็อตหมดอายุ (Owner เท่านั้น) |
| GET/PUT | `/staff/orders...` | Kitchen/Serving Queue |

### Internal UI

- `owner/MenuManagement.tsx`: โหลด ingredient registry และแยกแท็บเมนู/portion preset
- `owner/MenuItemsTab.tsx`: สร้าง/แก้ไข/หยุดขาย/ลบเมนู, BOM, รูป, dynamic category registry และ responsive layout
- `owner/PortionPresetsTab.tsx`: UI ใช้กรัมทั้งหมดและแปลงเป็น kg ก่อนเรียก API
- `owner/NotFreshInventory.tsx`: แสดงเฉพาะล็อตหมดอายุที่ยังมีของและมี dialog ยืนยันแยกทิ้ง
- `owner/SystemLogs.tsx`: เปลี่ยน JSON table เป็น activity cards ภาษาไทยพร้อมค้นหา ผู้ดำเนินการ เวลา และรายละเอียด
- `owner/Dashboard.tsx` และ `staff/StaffDashboard.tsx`: ตัวเลขสถานะไม่นับล็อตยอดศูนย์
- `staff/ReceiveLot.tsx`: สร้าง ingredient ID ใหม่ได้ แต่ Staff กำหนด portion preset ไม่ได้
- `staff/KitchenQueue.tsx`: หน้าแจ้งเตือน/เตรียมสต็อกของครัว
- `staff/OrdersToServe.tsx`: Serving Queue สำหรับติดตามและยืนยันออเดอร์
- `routes.tsx` และ `sidebar.tsx`: แยก Kitchen/Serving routes และไม่เปิดหน้าจัดการของหมดอายุให้ Staff

### Customer UI

- หน้าเมนูอ่าน category, image และ available servings จาก API
- แสดงเฉพาะเมนู active ที่ไม่ถูก soft-delete
- หมวดหมู่ในหน้าลูกค้าสร้างจาก category ของเมนูที่ API ส่งกลับโดยอัตโนมัติ
- API base URL รองรับ path รูปเมนูจาก API

## 3. Database migrations ใหม่

ต้องรันตามลำดับ ห้ามข้ามไฟล์:

1. `0007_menu_catalog.sql` — เพิ่ม category/image/sort metadata ใน `menu_items`
2. `0008_order_bom_snapshot.sql` — เพิ่ม `order_item_bom`, backfill และแก้ `auto_confirm_order()` ให้ใช้งาน snapshot
3. `0009_rename_meat_menu_category.sql` — เปลี่ยนชื่อหมวด `เนื้อ` เป็น `เนื้อสัตว์`
4. `0010_menu_soft_delete.sql` — เพิ่ม `menu_items.is_deleted`
5. `0011_menu_categories.sql` — เพิ่มทะเบียน `menu_categories` และ seed/backfill หมวดเดิม

ฐานข้อมูลที่เชื่อมกับเครื่องผู้พัฒนาปัจจุบันถูก apply `0007`–`0011` แล้ว แต่ environment ของผู้พัฒนาคนอื่น, staging และ production ต้อง apply เอง

หลัง migrate ควรตรวจอย่างน้อย:

```sql
SELECT column_name
FROM information_schema.columns
WHERE table_name = 'menu_items';

SELECT to_regclass('public.order_item_bom');
SELECT to_regclass('public.menu_categories');
```

คอลัมน์สำคัญที่ต้องมีใน `menu_items`: `category`, `image_path`, `image_alt`, `sort_order`, `is_deleted`

## 4. Invariants ที่ห้ามทำพัง

- ห้าม hard-delete เมนูที่มีออเดอร์เก่า ให้ใช้ `is_deleted = true` และ `is_active = false`
- ห้ามคำนวณออเดอร์เก่าจาก `menu_item_ingredients`; ต้องใช้ `order_item_bom`
- ห้ามนับล็อตยอดศูนย์ใน Dashboard/FIFO/active stock
- ห้ามให้ Staff ส่งหรือแก้ `defaultPortionSizeKg`
- ห้ามแยกทิ้งล็อตที่ยังไม่หมดอายุ หรือให้ Staff ใช้ disposal endpoint
- การ rename หมวดต้องอัปเดต `menu_items.category` และ `menu_categories.name` ใน transaction เดียว
- หมวดที่ยังมีเมนู active/non-deleted ใช้งานอยู่ลบไม่ได้ ต้องย้ายหรือลบเมนูก่อน

## 5. ประเด็นที่ต้องระวัง/งานถัดไป

### รูปเมนู

ปัจจุบันไฟล์ถูกเก็บใน `apps/api/uploads/menu` และ path ถูกเก็บใน DB วิธีนี้มีข้อจำกัด:

- local filesystem อาจหายเมื่อ redeploy
- หลาย API instances จะไม่เห็นไฟล์ชุดเดียวกัน
- ไฟล์ใน working tree เป็นข้อมูล runtime ไม่ควร commit โดยไม่ตั้งใจ

ก่อน production ควรย้ายไป Supabase Storage/S3-compatible object storage และเพิ่ม ignore rule สำหรับ runtime uploads ตาม deployment policy ของทีม

### Tags

ข้อสรุปเชิงออกแบบคือหนึ่งเมนูมีหนึ่งหมวดหลักและหลาย Tags ได้ เช่น:

- หมวดหลัก: `เนื้อสัตว์`
- Tags: `เนื้อวัว`, `ริบอาย`, `พรีเมียม`

ยังไม่มี tables/API/UI สำหรับ Tags หากทำต่อควรใช้ many-to-many (`menu_tags`, `menu_item_tags`) และไม่เปลี่ยน category ให้เป็น array

### Category edit UI

- ฟอร์มสร้างเมนูอ่านรายการจาก `menu_categories` และมีปุ่ม “จัดการหมวด” สำหรับเพิ่ม/rename/delete
- การ rename เปลี่ยนเมนูเดิมทุกเมนูในหมวดนั้น
- ตรวจต่อว่ dropdown ใน edit card ใช้ dynamic categories ครบทุกกรณี โดยเฉพาะหมวดที่เพิ่งเพิ่มใหม่

### System logs

- UI มี mapping ภาษาไทยสำหรับ actions ที่รู้จัก
- action ใหม่ที่ไม่มี mapping จะแสดงเป็น “กิจกรรมระบบ” พร้อมชื่อ action ดิบ
- เมื่อเพิ่ม action ใหม่ควรเพิ่ม metadata/labels ใน `owner/SystemLogs.tsx`

## 7. Checklist ก่อน commit/push

1. รัน `git status --short` และตรวจว่าไม่ stage รูปจริงใน `apps/api/uploads/menu` โดยไม่ตั้งใจ
2. ตรวจ diff โดยเฉพาะ `apps/api/src/index.ts` ซึ่งรวมหลาย feature ในไฟล์เดียว
3. รัน migrations `0007`–`0011` ใน environment เป้าหมายตามลำดับ
4. Restart API หลัง migrate schema/code changes
5. รันคำสั่ง:

   ```powershell
   npm run build --workspace=api
   npm run build --workspace=internal
   npm run build --workspace=customer
   npm test --workspace=api
   git diff --check
   ```

6. Smoke test ด้วยบัญชีแต่ละ role:
   - Owner: สร้างเมนู + BOM, เพิ่ม/rename หมวด, upload รูป, หยุดขาย, soft-delete, ตั้ง preset เป็นกรัม, แยกทิ้งล็อต
   - Staff: สร้าง ingredient ใหม่, รับล็อต, โอนไป Prep, ดู Kitchen Queue, ยืนยัน Serving Queue และยืนยันว่าแก้ preset/แยกทิ้งไม่ได้
   - Customer: เปิด QR session, กรองหมวด, ดูรูป/จำนวนพร้อมขาย, สั่งเมนู และตรวจว่าเมนูที่ปิด/ลบไม่แสดง
   - Cashier: ตรวจว่า check-in/payment flow เดิมยังทำงาน
